# 05 – רשימת קרדנציאלים והרשאות מדויקות נדרשות

**חשוב: שום קרדנציאל לא התבקש בפועל עדיין, ושום קרדנציאל לא צריך להישלח בצ'אט הזה. זהו מסמך תכנון בלבד – מפרט מוכן להעברה למי שמנהל את חשבונות הוורדפרס/גוגל של איקום, לביצוע כשתאשרו.**

## סיכום מהיר

| # | קרדנציאל | סוג | היקף הרשאה מדויק | למה נדרש | סטטוס |
|---|---|---|---|---|---|
| 1 | WordPress Application Password | Application Password (ליבת וורדפרס, ללא תוסף) | משתמש ייעודי חדש, תפקיד **Contributor בלבד** | יצירת טיוטות פוסט בלוג בלבד | טרם סופק |
| 2 | Google Cloud Service Account – Search Console | קובץ מפתח JSON | Scope: `webmasters.readonly` בלבד; מתווסף כמשתמש **Restricted** בהגדרות ה-property ב-Search Console | קריאת נתוני ביצועי חיפוש | טרם סופק |
| 3 | Google Cloud Service Account – Analytics | קובץ מפתח JSON (יכול להיות אותו service account כמו #2 או נפרד) | Scope: `analytics.readonly` בלבד; מתווסף כתפקיד **Viewer** ב-GA4 Property Access Management | קריאת נתוני תנועה/מעורבות | טרם סופק |
| 4 | *(עתידי, אופציונלי בלבד)* Google Sheets API | קובץ מפתח JSON | Scope מוגבל ל**קובץ גיליון ספציפי אחד** ששותף ידנית עם ה-service account – **לא** הרשאת Drive רחבה | שדרוג עתידי אפשרי של קובץ האישור המקומי לגיליון חי | טרם נדרש בכלל – רק אם יוחלט לעבור מ-CSV מקומי |

## פירוט #1 – WordPress Application Password

**מה זה:** פיצ'ר מובנה בליבת וורדפרס (מגרסה 5.6 ואילך) שמאפשר אימות API בלי לחשוף את סיסמת המשתמש הרגילה. כל Application Password ניתן לביטול נפרד בכל רגע מ-wp-admin, בלי לגעת בסיסמת הכניסה הרגילה.

**איך יוצרים (לביצוע המשתמש/מנהל האתר, לא הסוכן):**
1. יצירת משתמש וורדפרס **חדש וייעודי** (למשל `seo-agent`), **לא** שימוש במשתמש קיים.
2. הגדרת תפקיד המשתמש: **Contributor**. לא Author, לא Editor, לא Administrator (ראו הסבר מלא ב-`SAFE_INTEGRATION_PLAN.md` סעיף 2 – Contributor הוא היחיד שחסום ברמת השרת מלפרסם ומלערוך עמודים).
3. בתוך פרופיל המשתמש → Application Passwords → יצירת סיסמה חדשה בשם ברור (למשל "SEO Agent - Draft Creation").
4. שמירת הסיסמה שנוצרת במקום מאובטח (מנהל סודות / משתני סביבה) – **לא** בקובץ שנכנס ל-git, **לא** בהודעת צ'אט.

## פירוט #2+#3 – Google Cloud Service Account

**מה זה:** "משתמש רובוט" ב-Google Cloud שמאומת דרך קובץ מפתח JSON במקום סיסמה אנושית, ומקבל גישה מוגבלת בדיוק לפי מה שמשתפים איתו.

**איך יוצרים (לביצוע המשתמש):**
1. ב-Google Cloud Console: יצירת פרויקט (אם אין כבר), יצירת Service Account.
2. הפעלת ה-API הרלוונטי בפרויקט: Search Console API / Google Analytics Data API.
3. הורדת קובץ מפתח JSON עבור ה-service account.
4. **בצד Search Console:** Settings → Users and permissions → Add user → הזנת אימייל ה-service account → הרשאה **Restricted**.
5. **בצד GA4:** Admin → Property Access Management → Add users → הזנת אימייל ה-service account → תפקיד **Viewer**.
6. שמירת קובץ ה-JSON במקום מאובטח בלבד.

## עקרונות אחסון קרדנציאלים (לכל הפריטים לעיל)

- **לעולם לא** בקובץ שנכנס ל-git (כולל לא בתיקיית `data/` של הפרויקט הזה).
- **לעולם לא** מודבק בהודעת צ'אט/שיחה עם הסוכן.
- מומלץ: משתני סביבה בסביבת ההרצה בפועל, או מנהל סודות ייעודי (Secret Manager).
- מומלץ: רוטציה תקופתית (יצירת Application Password/מפתח חדש והשבתת הישן, כל כמה חודשים).
- כל קרדנציאל **נפרד** ומוגבל למטרתו בלבד – לא קרדנציאל אחד "כללי" לכל הפעולות.

## מתי בפועל תתבקשו לספק את אלה

**רק** לאחר שתאשרו במפורש להתחיל שלב הטמעה (ראו `SAFE_INTEGRATION_PLAN.md`, סעיף 8 – "השלבים הבאים"), ורק אחד בכל פעם: קודם שער האישור (`04_approval_gate_plan.md`, לא דורש קרדנציאל כלל כי הוא קורא קובץ מקומי), אחר כך ה-imports לקריאה בלבד (#2, #3), ורק בסוף – אם עדיין תרצו – יצירת הטיוטות (#1).
