# 04 – תוכנית טכנית: שער אישור לפני יצירת טיוטת וורדפרס

**מצב: תכנון בלבד. לא מוטמע.** זהו המסמך הקריטי ביותר בשכבת האינטגרציה – שום קוד יצירת טיוטה (`01_wordpress_draft_creation_plan.md`) לא מוטמע לפני שהמנגנון הזה קיים ונבדק.

## מטרה

לוודא **ברמת קוד**, לא רק ברמת מדיניות/הנחיה, ששום טיוטת וורדפרס לא נוצרת ללא אישור אנושי מפורש ורשום.

## מקור האמת

`data/approval/approval_log.csv` (מבנה מלא: `data/approval/README.md`).

## הלוגיקה המתוכננת (פסאודו-קוד, לא מוטמע)

```
for row in read_csv("data/approval/approval_log.csv"):
    if row.wp_draft_clearance != "Yes":
        continue  # אין אישור - הפריט לא נוגע
    if row.draft_created == "Yes":
        continue  # כבר נוצרה טיוטה - אין כפילות
    if row.cleared_by == "" or row.cleared_date == "":
        log_warning(f"{row.item_id}: wp_draft_clearance=Yes אך חסר cleared_by/cleared_date - נחסם")
        continue  # אישור לא שלם - נחסם לביטחון, לא ממשיכים בניחוש
    # רק כאן, ורק כאן, מותר לעבור להליך יצירת הטיוטה (01)
    proceed_to_wordpress_draft_creation(row)
```

**עיקרון מפתח:** ברירת המחדל היא תמיד "לא לפעול". רק שילוב מדויק של `wp_draft_clearance=Yes` **וגם** `cleared_by`+`cleared_date` מלאים **וגם** `draft_created != Yes` מתיר המשך. כל מצב חריג/חלקי/לא ברור → נחסם ונרשם ליומן, לא מנוחש.

## מי יכול לשנות `wp_draft_clearance` ל-`Yes`

**רק אדם, ידנית, בקובץ עצמו.** הסוכן:
- **יכול** להציע/לסמן שורה כמוכנה לבדיקה (למשל להוסיף שורה חדשה עם `wp_draft_clearance=No`).
- **לעולם לא** כותב בעצמו `Yes` בעמודה הזו, גם אם המשתמש מבקש זאת בשיחה – שינוי שדה זה נעשה בעריכה ישירה של הקובץ, כפעולה מכוונת ומתועדת (הקובץ תחת git – כל שינוי נראה ב-diff).

## הבדל בין שני שערי האישור

| שער | איפה מתועד | מי קובע | מה הוא מתיר |
|---|---|---|---|
| אישור תוכן (`content_status=Approved`) | `docs/09_APPROVAL_PROCESS.md` | אדם, לפי בדיקת תוכן/טון/דיוק | שהתוכן עצמו מוכן מבחינה איכותית |
| אישור יצירת טיוטת וורדפרס (`wp_draft_clearance=Yes`) | `data/approval/approval_log.csv` | אדם, בנפרד ובמפורש | שמותר להריץ פעולת API שיוצרת טיוטה בפועל בוורדפרס |

אלה **שני שערים נפרדים בכוונה**, כדי שאישור תוכן לא "יזלוג" אוטומטית להרשאת פעולה טכנית על מערכת חיה.

## לוגים

כל בדיקה של השער – גם כזו שלא עברה – נרשמת (item_id, תוצאה, סיבה אם נחסם) לצורך שקיפות ומעקב, ולא רק ההרצות שהצליחו.

## מעבר עתידי ל-Google Sheet חי

אם וכאשר יוחלט על כך: אותה לוגיקה בדיוק, רק מקור הקריאה משתנה מ-`csv.DictReader` מקומי ל-קריאה דרך Sheets API (למשל ספריית `gspread` או קריאת REST ישירה ל-Sheets API v4), עם קרדנציאל service account המוגבל **לקובץ הגיליון הספציפי בלבד** (לא Drive-wide) – ראו `05_credentials_checklist.md`. הכתיבה לעמודת `wp_draft_clearance` נשארת פעולה אנושית ידנית בגיליון, לעולם לא נכתבת אוטומטית על ידי הסוכן.

## דרישות קדם לפני הטמעה בפועל

1. אישור מפורש מהמשתמש להתחיל הטמעה.
2. `data/approval/approval_log.csv` קיים במבנה הנכון (כבר קיים).
3. בדיקות (tests) לכל ארבעת המצבים: אישור מלא ותקין / אין אישור / אישור חלקי (`Yes` בלי `cleared_by`) / כבר נוצרה טיוטה בעבר – לפני חיבור לקריאת API אמיתית.
